# 引擎健康检查请求协调

Status: ready-for-agent

## Problem Statement

顶栏、工作台与设置页分别检查引擎状态，同一时刻会独立发出请求。健康检查沿用生成请求的 120 秒等待上限，慢响应时会积压状态查询，设置页迟迟不能结束检查。

## Solution

共享正在进行的健康检查，最多等待 10 秒。请求成功或失败后立即释放，下一次检查重新请求，避免首次离线状态妨碍引擎启动后的恢复。

## User Stories

1. 作为使用者，我希望多个页面同时检查状态时只发送一次请求，减少重复查询。
2. 作为使用者，我希望状态查询最多等待 10 秒，及时收到失败反馈。
3. 作为使用者，我希望引擎恢复后可以重新检查，不被已失败的请求卡住。
4. 作为使用者，我希望成功后再次检查能获取最新状态，而非缓存结果。
5. 作为使用者，我希望生成、导出和试听保持现有行为。
6. 作为维护者，我希望通过现有健康检查 interface 验证行为，不依赖真实引擎、音频或付费接口。

## Implementation Decisions

- 在现有引擎请求 module 内加深健康请求生命周期，保留 getHealth() 的参数与返回类型以及所有调用点。
- 只复用正在进行的 Promise；成功、HTTP 失败、连接失败或超时后均释放，不缓存结果。
- 健康请求单独使用 10 秒超时；其他请求保持 120 秒。
- 保留现有错误处理、请求正文和请求头语义，不增加自动重试。
- 不改变数据结构、配置、安装包、路径、环境变量、MCP 权限或依赖。

## Testing Decisions

- 用户已确认以现有 getHealth() interface 为测试 seam；生产 fetch adapter 使用真实网络，测试 adapter 使用可控 Promise 与 Response。
- 断言并发调用只发一次请求且返回相同结果；成功后新调用再次请求。
- 断言 HTTP 失败、连接失败与超时能传播给所有等待者；随后调用能恢复。
- 捕获超时 signal 工厂参数验证 10000ms，并触发受控超时验证释放；不真实等待 10 秒。
- 验证普通请求仍为 120000ms，生成/导出请求不会被合并。
- 测试脚本仅放系统临时目录；运行构建、现有工作台回归及新增播放回归。

## Out of Scope

拆分工作台、生成调度、项目存储、拆句、路径、MCP、错误协议统一、TTS 超时预算、轮询频率与结果缓存均不在本次范围。

## Further Notes

只承诺减少同时发出的重复状态请求和限制等待时间，不声称真实启动或切章耗时已改善。已先修复同源单句试听保留连续队列结束回调的问题，作为本分支独立 bug 修复。
